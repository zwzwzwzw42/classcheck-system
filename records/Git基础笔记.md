# Git 基础笔记（课堂作业版）

> 用"写论文/游戏存档"的类比理解 Git，配合本项目实际操作记录。

## 1. Git 是什么

Git 是一个**版本管理工具**：把项目文件的每次改动记录成一个个"存档点"，随时可以回到任意历史版本，也能看到每次改了什么。

类比：
- **提交（commit）** = 游戏存档 / 论文的一个版本
- **分支（branch）** = 平行世界的一条剧情线
- **仓库（repository）** = 整个游戏的存档库（本项目就是 `D:\classcheck_system` 这个文件夹）

## 2. 三个区域（理解 add 和 commit）

```
工作区          暂存区           版本库
你正在编辑的文件  →  git add  →  准备好的改动  →  git commit  →  永久存档
```

- **工作区**：你在文件夹里看到、正在改的文件
- **暂存区**：`git add` 后，改动被"挑出来"准备提交
- **版本库**：`git commit` 后，改动永久保存为一个版本

为什么分两步：可以一次只提交相关的文件，让每个"存档"主题清晰。

## 3. 最常用命令（本项目实际在用）

| 命令 | 作用 | 类比 |
|---|---|---|
| `git status` | 查看当前改了哪些文件、哪些待提交 | 看存档前的状态 |
| `git add -A` | 把所有改动放进暂存区 | 选定要存档的内容 |
| `git commit -m "说明"` | 提交一个版本，附一句说明 | 存档并写备注 |
| `git log --oneline` | 查看历史提交列表（一行一条） | 翻看所有存档 |
| `git diff` | 查看还没提交的具体改动 | 对比改了哪几行 |
| `git restore 文件名` | 丢弃某文件未提交的修改，恢复到上次提交 | 读档（放弃本次改动） |

本项目的标准保存动作（我每次都在执行）：
```bash
git add -A
git commit -m "feat: 完成了xxx功能"
```

## 4. 提交说明的写法

提交信息前面加类型前缀，一眼看出这个版本干了什么：
- `feat:` 新功能（如 feat: 完成认证模块）
- `fix:` 修 bug
- `docs:` 文档
- `chore:` 杂项配置（如装 Maven、改 .gitignore）
- `style:` 只改样式
- `refactor:` 重构（不改功能）

## 5. 分支 branch / master / main

- **分支**是一条独立的开发时间线。默认主分支叫 **master**（新版 Git/GitHub 默认叫 **main**，两者只是名字不同，都是主分支）。
- 本项目当前就在 **master 分支**上，所有提交都在这条主线上。
- 典型用法：开发新功能时开一条新分支，改坏了不影响主线；做好了再**合并（merge）**回主线。
  ```bash
  git switch -c feature-login   # 新建并切换到 feature-login 分支
  # ...在分支上开发、提交...
  git switch master             # 切回主分支
  git merge feature-login       # 把新功能合并进主线
  ```
- **本作业规模不大，我建议就一直用 master 主线开发**，每个模块一个提交，简单清晰；分支是多人协作或大功能才需要的高级操作，了解即可。

## 6. .gitignore 是什么

`.gitignore` 文件列出"不纳入版本管理"的文件，例如本项目忽略了：
- `target/`（Maven 编译产物，可重新生成）
- `tools/`（本地 Maven 工具，体积大）
- `.idea/`（IDEA 的个人配置）

这些文件不需要存档，也不会出现在提交里。

## 7. 远程仓库（了解）

前面讲的都是**本地仓库**（在你电脑上）。GitHub、Gitee 是**远程仓库**网站：
- `git push`：把本地提交上传到远程（备份 + 分享）
- `git pull`：把远程的最新改动拉到本地
- `git clone 网址`：把网上的项目下载到本地

本作业只在本地用 Git 即可，不强制用远程；如果想备份/防丢，可以传到 Gitee（国内快）。

## 8. 出问题怎么办（作业最实用的几招）

| 情况 | 处理 |
|---|---|
| 改坏了，想回到上次提交的状态 | `git restore 文件名`（只放弃未提交改动） |
| 想回到很久以前的某个版本看看 | `git log --oneline` 找到版本号，`git switch 版本号前7位` |
| 提交后发现漏了文件 | 再 add + commit 一次即可 |
| 想看某个文件是谁/什么时候改的 | `git log --oneline 文件名` |

> 重要原则：**每完成一个能运行的小阶段就提交一次**。这样即使后面改崩了，随时能回到最近的正常版本——这也是指导手册里"注意代码版本"的要求。
